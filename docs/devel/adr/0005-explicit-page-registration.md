# ADR-0005: マルチページは規約ベースではなく明示登録を既定とする

- 状態: Accepted
- 日付: 2026-06-05
- 関連: `core/src/main/java/io/streamlit4j/core/St.java`（`pages`）/ `core/src/main/java/io/streamlit4j/core/domain/Page.java`

## Context

マルチページアプリの登録方式に次の 2 案があった。

1. **規約ベース**: `pages/` ディレクトリーや `@StPage` アノテーションを起動時にスキャンして自動登録
2. **明示登録**: `St.pages(List.of(new Page("Home", "/", Home::run), ...))` のように引数で渡す

Streamlit Python は #1 の規約（`pages/` ディレクトリー）。

## Decision

**明示登録（`St.pages(List<Page>)`）を既定**とする。規約ベース自動登録は提供しない。

主な理由:

- **GraalVM 整合性**: classpath スキャン / `@StPage` アノテーション読み込みは
  リフレクションを要し、[ADR-0004](./0004-graalvm-deferred.md) の v1.x 以降の
  GraalVM ネイティブ化を阻害する
- **IoC 非依存の維持**: 自動スキャンを実装するには Spring 等のコンテナーへの依存か、独自スキャナー実装が必要。`core` モジュールをフレームワーク非依存に保つ方針と整合
- **順序・条件付き登録**: `List<Page>` を渡す API なので、ページ順序が一意に決まり、条件分岐や動的生成も自然に書ける（規約ベースだと並び制御に追加メタデータが必要）
- **テストでの再現性**: 登録内容が呼び出しコードに明示的に出るため、テストで一部ページだけを差し替えやすい
- **拡張余地は残す**: 将来 backlog として規約ベース自動登録を追加検討する余地はあるが、初版では複雑化を避ける

## Consequences

良い影響:

- ページ列挙のためのクラスパススキャンが不要 → GraalVM ネイティブ化（[ADR-0004](./0004-graalvm-deferred.md)）との相性が良い
- ページ順序が明示的で予測可能
- 同一クラスから複数ページを派生させたり、条件付きでページを除外したりが素直に書ける
- Spring Boot 統合でも特別な Bean スキャンが不要

悪い影響:

- ページ追加時に登録呼び出し側に手を入れる必要がある
- Streamlit からの移行ユーザーは「`pages/` に置けば自動登録される」期待と異なる

## Alternatives Considered

- **`pages/` 規約**: クラスパススキャン / リフレクションが必須で、ネイティブ化障壁になる
- **`@StPage` アノテーション**: 同じくスキャンが必要
- **両対応**: 二重メンテナンスは初期コストに見合わない。将来 backlog として規約ベースを追加検討する余地は残す
