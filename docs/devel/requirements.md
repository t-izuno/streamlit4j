# streamlit4j 要件定義書

> ステータス: ドラフト v0.3
>
> 種別: OSS フレームワーク（公開前提）
>
> 目標スコープ: Streamlit 互換フル志向（マルチページ・状態・カスタムコンポーネント）
>
> 関連ドキュメント: 仕様は `specification.md`、設計は `design.md`、実行計画は `tasks/task.md`

## 1. 背景と目的

Streamlit は Python でデータアプリを最小コードで構築できる点で普及した。
一方 JVM エコシステムには「スクリプトを書く感覚でインタラクティブな Web アプリを作れる」
軽量フレームワークが乏しい。先行する Javelit（旧 Jeamlit）が存在するが、
本プロジェクト streamlit4j は OSS として公開し、後発の利を活かした明確な差別化を狙う。

達成したいこと:

- JVM 上で Streamlit の「再実行モデル」を再現し、Java 開発者がフロント実装なしで
  データアプリ・管理画面を構築できるようにする
- 既存の Java 資産（Spring Boot / Quarkus のサービス層・ドメインモデル）を
  活かしたまま組み込める
- Streamlit からの移行・知識転用がしやすい、高い API 親和性を提供する

非目標（このプロジェクトでやらないこと）:

- 汎用 SPA フレームワークの置き換え（リッチな業務 SPA は対象外）
- ピクセル単位の自由なレイアウト編集機能
- ノーコード GUI ビルダー

ブランディング方針（確定）:

- プロジェクト名は `streamlit4j` とする。`4j` サフィックスは Java エコシステムで
  独立した派生・互換実装を示す慣行であり、langchain4j（LangChain ブランド名 +
  `4j`、Apache-2.0、Maven Central 公開、主要ベンダー参照）という運用上の前例がある
- README と公式ドキュメント冒頭で「Snowflake 社および Streamlit プロジェクトとは
  無関係の独立コミュニティ OSS である」旨を明示する（nominative fair use の
  第三要件を担保）
- Streamlit のロゴ・カラーパレット・公式マークは使用せず、独自の視覚アイデンティティーを
  構築する

## 2. ターゲットユーザーとユースケース

想定ユーザー:

- 社内管理画面・バックオフィスを短時間で作りたい Java エンジニア
- データ可視化・レポート・API ショーケースのプロトタイプを作る開発者
- LLM / AI エージェントの操作 UI を Java（LangChain4j など）で組みたい開発者

主要ユースケース:

- 単一の `.java` ファイルを CLI で即起動するプロトタイピング
- 既存 Spring Boot アプリへ管理ダッシュボードを 1 エンドポイントとして埋め込み
- 社内データを対象とした可視化ダッシュボード
- AI エージェントのチャット UI とツール実行画面

## 3. ポジショニングと差別化

### 3.1 ポジショニング

| 観点 | Streamlit (Python) | Javelit (Java) | streamlit4j（狙い） |
| --- | --- | --- | --- |
| 言語 | Python | Java | Java |
| 実行モデル | スクリプト全体を再実行 | main() を再実行 | エントリポイントを再実行 |
| 既存アプリ埋め込み | 弱い | 可能 | Spring Boot / Quarkus を一級サポート |
| 起動速度 | 遅い（Python） | JVM 起動 | GraalVM native image を視野 |
| 同時セッション | プロセス前提 | スレッド | 仮想スレッド前提設計 |
| API 親和性 | 基準 | 独自（`Jt.x().use()`） | Streamlit 命名へ最大限寄せる |
| カスタム部品 | React + iframe | あり | 型安全宣言 + TS SDK + 雛形生成 |

### 3.2 差別化の柱

- **API 親和性**: メソッド名・引数順を Streamlit に極力合わせ、Python の知識と
  サンプルをほぼそのまま移植できる状態を目指す。Javelit の独自流儀に対する差別化軸。
- **フレームワーク統合**: Spring Boot Starter と Quarkus Extension を一級提供。
  既存の認証・セッション・DI に乗せて組み込める。
- **スケーラビリティー**: セッションごとの再実行を仮想スレッドで処理する設計。
  数千セッションを安価に捌くことを JVM の強みとして打ち出す。
- **起動と省メモリー**: GraalVM native image 対応を中期目標に置き、Python では
  難しい高速起動・低フットプリントを実現する。
- **型安全**: 状態（state）とカスタムコンポーネントの境界に Java の型システムを
  効かせ、ランタイムエラーをコンパイル時に寄せる。

## 4. スコープ

### 4.1 v1 に含む

- コア再実行モデルとセッション管理
- 入力系ウィジェット（slider, text_input, number_input, selectbox, multiselect,
  checkbox, radio, button, date_input, file_uploader ほか）
- 表示系要素（write, markdown, title, header, metric, dataframe, table, json,
  code, 主要チャート）
- レイアウト（columns, container, expander, tabs, sidebar）
- セッション状態（session_state 相当）と型付きアクセサー
- マルチページアプリ
- フォーム（batch 送信）
- キャッシュ（data / resource の 2 種）
- カスタムコンポーネント SDK（型安全宣言 + TS フロント連携 + 雛形生成 CLI）
- テーマ（ライト / ダーク / カスタムカラー）
- 実行形態: スタンドアロン CLI と Spring Boot 埋め込み
- ライブリロードによる開発体験

### 4.2 v1 で対象外（将来検討）

- Quarkus Extension（v1.1 を目安）
- GraalVM native image 公式サポート（v1.x）
- 共有・ホスティング基盤（Streamlit Community Cloud 相当）
- リアルタイム協調編集
- SSE / WebSocket 以外のトランスポート（gRPC など）

## 5. 機能要件

利用者目線（開発者 / アプリ利用者 / 運用者）で「何ができるか」を定義する。
API シグネチャーやプロトコル詳細は `specification.md`、
内部実装方式は `design.md` を参照する。

ステークホルダー定義:

- **開発者**: streamlit4j を使ってアプリを実装する Java エンジニア
- **アプリ利用者**: 開発者が作ったアプリをブラウザーから操作するエンドユーザー
- **運用者**: 本番環境で streamlit4j アプリを運用する担当者

### 5.1 コア再実行モデル

- 開発者は単一のエントリポイントを書くだけでインタラクティブなアプリを構築できる
- アプリ利用者は UI を操作するたびに、最新の状態が自動で反映された画面を見られる
- 開発者は明示的な再実行・中断をコードからトリガーできる
- 開発者は同じ画面内で同種ウィジェットを複数配置しても、それぞれの値が正しく
  区別されることを期待できる

### 5.2 表示要素・ウィジェットカタログ

- 開発者は v1 提供の主要 40 要素を組み合わせて、フロント実装なしに UI を構成できる
- 開発者は入力系・表示系・レイアウト系・状態系の 4 カテゴリーから必要な要素を
  選べる

### 5.3 セッション状態管理

- 開発者はセッションごとの状態を型安全に保持・読み書きできる
- アプリ利用者は再実行や画面更新をまたいでも、自分の入力やウィジェット選択が
  保持された状態でアプリを使い続けられる
- 開発者はセッションのライフサイクル（生成・タイムアウト・破棄）にフックして
  独自処理を差し込める

### 5.4 レイアウトとコンテナー

- 開発者は列分割・領域・折りたたみ・タブ・サイドバーを組み合わせて画面を構成できる
- 開発者はレイアウトをネストして複雑な画面構造を表現できる
- 開発者は描画後に内容を差し替えられるプレースホルダーを使える

### 5.5 マルチページ

- 開発者は規約ベースまたは明示登録のいずれかでマルチページアプリを構築できる
- アプリ利用者はナビゲーション UI と URL ディープリンクで任意のページに
  直接アクセスできる

### 5.6 フォーム

- アプリ利用者は複数項目を編集してから送信ボタンでまとめて反映できる
- 開発者はフォーム単位で再実行回数を抑え、入力途中の中間状態を扱わずに済む

### 5.7 キャッシュ

- 開発者はコストの高い関数結果をキャッシュして再実行間で再利用できる
- 開発者は DB コネクションなどのリソースをセッション間で安全に共有できる
- 開発者は引数ハッシュと TTL でキャッシュ無効化を制御できる

### 5.8 カスタムコンポーネント

- 開発者は React で独自コンポーネントを実装してアプリに組み込める
- 開発者は信頼境界が必要なケースで iframe 隔離コンポーネントを選択できる
- 開発者はコンポーネントの引数・戻り値を Java の型で宣言してコンパイル時に
  検証できる
- 開発者は CLI で雛形を生成し、コンポーネント開発をすぐ始められる

### 5.9 テーマとスタイリング

- 開発者はライト / ダーク / カスタムカラーのテーマを設定で切り替えられる
- アプリ利用者はコントラスト比・キーボード操作・フォーカス可視のアクセシビリティーが
  確保された UI を享受できる

### 5.10 ファイルの入出力

- アプリ利用者はファイルをアップロードして処理結果を受け取れる
- アプリ利用者は CSV / 画像 / PDF などの生成物をダウンロードできる
- 開発者はアップロードのサイズ上限・MIME 制限・ストリーミング受信を設定できる

### 5.11 開発体験（ライブリロード）

- 開発者はソースを編集すると即座にブラウザーで結果を確認できる
- 開発者は実行時エラーを画面上のスタックトレースで原因特定できる
- 開発者は CLI コマンド一発でアプリを起動できる

### 5.12 実行形態

- 開発者は単一の `.java` ファイルをスタンドアロンで起動できる
- 開発者は既存 Spring Boot アプリの 1 エンドポイントとしてアプリを埋め込める
- 開発者はどちらの形態でも同一の App 定義を使い回せる

### 5.13 LLM UI

LLM / AI エージェントの操作 UI で、評価軸の全項目を最良水準に引き上げるための
要件を定義する。

- 開発者は LLM のトークン列を、SSE / WebSocket や差分メッセージの低レベル配線を意識せず、
  専用 API に渡すだけでチャット画面へ逐次表示できる
- アプリ利用者は生成中の Markdown が未完であっても、コードフェンス・表・リスト・数式が
  破綻しない状態で逐次表示されることを期待できる
- アプリ利用者は生成中に停止でき、停止後に同じ入力でリトライできる
- アプリ利用者は過去の入力を編集して再生成でき、編集前後の会話履歴が混線しない
- 開発者はコードブロック、表、数式、添付ファイル、ツール実行結果、カスタムコンポーネントを
  チャットメッセージ内に表示できる
- 開発者はチャット画面のレイアウト、メッセージ部品、入力欄、アクションボタンを
  カスタムコンポーネントまたはテーマで差し替えられる
- 運用者はスタンドアロン CLI 形態でも OIDC / OAuth によるログインと Cookie セッション維持を
  設定だけで有効化でき、認可コード交換と state 検証を経てセッションを開始できる

## 6. 非機能要件

### 6.1 パフォーマンスとスケーラビリティー

- 運用者は単一インスタンスで数千の同時セッションを処理できる
- アプリ利用者は UI 操作に対して低レイテンシーで応答が返ることを期待できる
- 運用者は差分送信により最小限のネットワーク量で配信できる

### 6.2 同時実行とセッション分離

- アプリ利用者は他セッションの状態に干渉されずに自分のセッションを利用できる
- 開発者はリソースキャッシュ等の共有リソースをスレッドセーフに扱える

### 6.3 セキュリティー

- 運用者は埋め込み時、ホストアプリの認証・認可・セッションを透過的に利用できる
- 運用者はアップロードファイルが必ずサイズ・形式の検証を経ることを保証できる
- 運用者は iframe component が sandbox 属性で隔離されていることを前提にできる
- 運用者はアプリ利用者からの入力値が常に検証されることを期待できる

### 6.4 可観測性

- 運用者は構造化ログ（セッション ID・再実行 seq・要素数・所要時間）で
  セッション挙動を追跡できる
- 運用者はメトリクス（アクティブセッション数・再実行レイテンシ・
  トランスポート接続数）で稼働状況を把握できる
- 運用者は将来的に OpenTelemetry に連携した可観測性スタックへ統合できる

### 6.5 互換性

- 開発者は JDK 21 LTS の機能（仮想スレッド・records・sealed・pattern matching）を
  前提に開発できる
- アプリ利用者はモダンブラウザー（Chrome / Edge / Firefox / Safari）で
  アプリを利用できる
- 開発者は Maven を基準に依存追加でき、Gradle 利用者向けの手順も参照できる

### 6.6 配布とパッケージング

- 開発者は Maven Central から streamlit4j を依存追加できる
- 開発者は用途に応じたモジュール（core / server / frontend-assets / cli /
  spring-boot-starter / examples）を選択して導入できる
- 開発者は事前ビルド済みのフロント静的アセットを意識せずに利用できる
- 開発者は JBang カタログ経由で CLI をインストールできる

### 6.7 LLM UI の検証可能性

- 開発者は外部 LLM API に依存しない Fake LLM で、固定トークン列を使った
  再現可能な E2E テストを実行できる
- 開発者は Playwright で実ブラウザーを起動し、トークン逐次表示、未完 Markdown の
  中間状態、停止、リトライ、編集後再生成を DOM とサーバー側イベントの両方で検証できる
- 開発者は SSE と WebSocket の両トランスポートについて、認証・プロキシ・再接続・
  生成中キャンセルの制約を同一シナリオで比較できる
- 運用者は packaged jar または CLI で起動した成果物に対して、`GET /` の 200 応答、
  フロント静的アセット配信、設定されたトランスポート接続確立、初期レンダー完了を確認できる

## 7. リスクと対応

| リスク | 影響 | 対応 |
| --- | --- | --- |
| 商標とブランディングの誤認 | Snowflake 社や Streamlit プロジェクトとの関連性が誤って想起される可能性 | langchain4j を前例として `streamlit4j` を採用。README とドキュメント冒頭に独立 OSS である旨の disclaimer を明記。ロゴ・カラーパレット・公式マークは流用せず、独自視覚 ID を構築 |
| フロント実装の工数 | SPA + プロトコルの開発負荷が大きい | PoC で薄く縦に通し、要素は段階追加 |
| Streamlit 機能の広さ | 互換フル志向はスコープが膨張しやすい | v1 を主要 40 要素に線引きし優先度管理 |
| LLM UI の実動作未検証 | API や部品が存在しても、生成中操作や未完 Markdown が実ブラウザーで破綻する可能性 | Fake LLM + Playwright の受入 E2E を必須化し、途中状態とサーバー側キャンセルまで検証する |
| Javelit との差別化が曖昧 | 後発として埋もれる | 統合・スケール・型安全の柱を一貫して打ち出す |
| カスタム component の安全性 | 埋め込み業務アプリでの XSS / 越権 | iframe sandbox・CSP・値検証を必須化 |
| プロトコル将来変更 | 互換性破壊 | エンベロープにバージョンを持たせ移行を管理 |
